# Dynamic GPU admission instrumentation smoke test

This versioned experiment demonstrates one narrow fact: with the same `concurrentGpuTasks=2` initial-estimate input in both modes, enabling the implemented dynamic estimator increased the observed stage-0 GPU task-admission maximum above two on this synthetic aggregation. It does not establish a performance benefit, and `concurrentGpuTasks=2` is an estimate input—not a hard task-count cap.

The mechanically validated result was:

- dynamic stage 0 maximum among successful task attempts: 8;
- static stage 0 observed maximum among successful task attempts: 2;
- zero failed task attempts in either application;
- identical SHA-256 for the complete canonical ten-row result;
- required GPU plan nodes: `GpuRange`, `GpuProject`, `GpuHashAggregate`, and `GpuColumnarExchange`.

Among recorded successful-task accumulator updates, dynamic mode exceeded two (reaching eight in the committed run), while all recorded static updates were two. Updates are emitted at task end, so their event-log order is completion order, not an acquisition-order controller timeline. Four successful static stage-0 attempts had no accumulator update; the validator therefore relies on the recorded maximum, reports attempt counts separately, and does not claim every task emitted the metric.

See [manifest.yaml](manifest.yaml) for identity, hashes, criteria, and limitations. [eventlog-summary.json](analysis/eventlog-summary.json) is the exact parser output, and [validated-summary.json](analysis/validated-summary.json) was generated by the versioned validator. Compressed raw event logs, stdout, and provenance checksums are committed under [raw](raw), [stdout](stdout), and [provenance](provenance).

Run with a new ID:

```bash
export SPARK_HOME=/path/to/spark-3.5.5
export RAPIDS_JAR=/path/to/rapids-4-spark_2.12-26.08.0-SNAPSHOT-cuda12.jar
export RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)"
./docs/experiments/dynamic-gpu-admission/run_experiment.sh
```

The runner refuses to reuse a run directory, requires exactly two newly generated logs, hashes complete results and artifacts, checks full-result equality and application IDs, rejects failed attempts or missing GPU plan nodes, and generates the verdict. A future performance experiment must rebuild the JAR from the target revision, randomize/counterbalance treatments, use repetitions, add actual memory pressure, and pre-register a latency estimand and uncertainty method.
