Scan split autotuner — team summary

NDS (TPC-DS) all 99 queries · SF100 · A5000 GPU · 16 of 64 CPU cores · 2026-07-15

The problem

Spark splits input files with a fixed maxPartitionBytes (128 MiB by default). For GPU scans that makes too many small tasks — each hands the GPU a tiny slice, so per-task overhead dominates and the GPU is underfed. A single fixed number can’t be right for every table, because tables compress and project differently.

What the change does

The autotuner sets the split per table, learning from that table’s own earlier reads:

decode ratio = decoded bytes / bytes read from disk     (measured on a prior read)
split        = batch size / decode ratio                (one task ≈ one GPU batch of work)
split        = clamp(split, Spark default, 4 GiB)       (never smaller than today; never above 4 GiB)

A table whose data shrinks when decoded gets a bigger split (fewer, fuller tasks); one that expands gets a smaller one. It never goes below Spark’s default, so it can only help or match.

Wins concentrate on scan-heavy queries (query9 3.8×, query59 2.9×, query28 2.7×) where the split grows from 128 MiB to 1–4 GiB and the task count drops ~20–30×. Small queries are unchanged.

Does a bigger GPU batch help? — mixed, needs to be understood

Raising the GPU batch from 1 GiB to 2 GiB is a wash on aggregate (1.70× vs 1.73×), but that average hides a real split in behavior:

2 GiB vs 1 GiBqueries
faster (>5%)27 (up to 3.9x)
slower (>5%)30
unchanged38
Open question: of the 27 queries that improved, only 3 had their split change — the other 24 were already at the 4 GiB cap, so the bigger batch itself sped them up, independent of the split. Batch size is not inert; it helps some query shapes and hurts others, and which shapes, and why, is not yet understood.

Why the aggregate is flat: scan time is barely spent on the GPU, so batch size only moves the small GPU-decode slice —

where scan time goesshare
Parquet footer read + row-group filtering (CPU, per file)~85%
reading data into host memory~8%
GPU decode~3%

The split win comes from fewer tasks. Understanding which query shapes benefit from a bigger batch (candidate: heavier per-batch GPU work downstream of the scan) is the open follow-up. Tests used only 16 of 64 cores, so the CPU-bound footer/filter step also has headroom.

Scaling up (planned: SF1000, SF10000)

The split decision has no total-data term — it depends only on the per-table decode ratio, which doesn’t change with scale. So:

scale factorparquet on disk (est.)expected
SF100 (measured)38 GB1.73x today
SF1000~380 GBsame splits, ~10x tasks, speedup holds
SF10000~3.8 TBsame splits, ~100x tasks, memory still flat

At SF1000/SF10000 we will measure: total runtime and speedup; per-query runtime, speedup, and split; scan task counts; and peak GPU memory + any spill — to confirm splits stay the same, tasks scale, and per-task memory stays ~1 GiB (no new out-of-memory risk).
