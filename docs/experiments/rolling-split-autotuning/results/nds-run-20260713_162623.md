# NDS Autotuner Run — 20260713_162623 (real TPC-DS queries)

First run of the scan split autotuner against **real NDS/TPC-DS queries** (not the synthetic
wide-projection microbench). Driven by `nds_power.py` over SF100 parquet, cold → warm.

## Setup
| Parameter | Value |
|---|---|
| Harness | `ab` repo `nds_power.py` + `nds-benchmark-listener` JAR |
| Data | NDS SF100 parquet, 24 tables (`parquet_sf100_decimal_fresh_20260623`) |
| Queries | `query9, query67, query76` (subset; same as prior mpb sweep) |
| GPU | RTX A5000, pinned by UUID `GPU-1aaa66fd` |
| Spark | 3.5.3, `local[16]`, 16 GB driver/executor, concurrentGpuTasks=2 |
| batchSizeBytes | 1 GiB |
| filecache | **disabled** (so cold→warm delta = split sizing, not caching) |
| Cold | empty history → COLD_START, 128 MiB splits, records per-table ratios |
| Warm | history present → DECIDED, autotuned per-table splits |

## Query runtimes — cold vs warm

| Query | Cold (128 MiB) | Warm (autotuned) | Speedup |
|---|---|---|---|
| query9 | 18.05s | 6.71s | **2.69×** |
| query67 | 8.94s | 8.31s | 1.08× |
| query76 | 13.25s | 7.57s | **1.75×** |
| **Power Test (sum)** | **40.0s** | **23.0s** | **1.74×** |

No crashes, no OOM, all queries succeeded on the A5000.

## Key finding — "expansion ratio" is a *projection ratio* on real queries

In the synthetic microbench, store_sales had ratio **1.146** (decoded > listed) because the
query summed 15 columns. Real NDS queries **project only a few columns and push predicates**,
so decoded bytes (just the scanned columns) are **far smaller** than listed on-disk bytes:
store_sales 0.30, catalog_sales 0.22, **web_sales 0.053**.

Consequence: `raw = batchSizeBytes / ratio` becomes very large, so **every large-table split
clamps to the batchSizeBytes ceiling (1 GiB)**. For real column-projected workloads the
autotuner effectively converges to *"set split ≈ batchSizeBytes"* — i.e. 1 GiB instead of the
128 MiB default (an 8× larger split, ~8× fewer scan tasks). **That alone delivers the 1.74×
power-test speedup here** — the win comes from raising the split to the batch ceiling, not
from fine per-table ratio differentiation (which matters more for wide-projection scans where
ratio > 1, as in the microbench).

### Design implications (not yet acted on)
1. **Per-table keying conflates projections.** The same table is scanned by different queries
   with different column sets → different ideal splits, but the autotuner keys only on table
   and uses `latestFor(label)`. Here it's moot (all clamp to ceiling), but a
   projection-aware key (table + column set) would matter for mixed workloads.
2. **Rename the concept.** For real queries this is a projection/selectivity ratio, not a GPU
   decode-expansion ratio.
3. **The ceiling is the real lever.** Since real ratios are <1, the split almost always equals
   batchSizeBytes. Raising the ceiling (e.g. 2 GiB, validated safe on this all-decimal data)
   is the knob that would push splits higher — see the 2 GiB microbench experiment.
